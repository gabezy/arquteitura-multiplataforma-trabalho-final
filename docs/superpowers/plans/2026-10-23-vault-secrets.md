# Vault for application secrets Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** No application secret is versioned; `catalog-service`, `compliance-service` and `bff-gateway` read their secrets from HashiCorp Vault at startup, locally via Docker Compose (issue #45).

**Architecture:** Vault runs in dev mode in the compose file. A one-shot `vault-init` job (like `kafka-init`) writes `secret/<service>` (KV v2) and creates one policy and one AppRole per service, with fixed `role_id`/`secret_id` taken from a root `.env` that is generated by `make env` and never committed. Each service logs in with its AppRole and reads only its own path before building its config; without Vault it does not start.

**Tech Stack:** HashiCorp Vault `hashicorp/vault:2.2.1`; Spring Cloud Vault (Spring Cloud `2025.1.4`, Spring Boot 4.1.1); Node 22 global `fetch` (no new dependency); Python `hvac`.

**Spec:** `docs/adr/0003-vault-para-secrets-das-aplicacoes.md` plus the decisions in this plan (agreed in the brainstorming of 2026-10-23).

## Global Constraints

- Vault paths (KV v2 mount `secret`, already enabled by dev mode) and keys, exactly:
  - `secret/catalog-service`: `db_username`, `db_password`
  - `secret/compliance-service`: `db_username`, `db_password`
  - `secret/bff-gateway`: `keycloak.client-secret`
- One policy and one AppRole per service, both named after the service; each policy is only `path "secret/data/<service>" { capabilities = ["read"] }`.
- Service env vars for Vault: `VAULT_ADDR` (default `http://localhost:8200`), `VAULT_ROLE_ID`, `VAULT_SECRET_ID` (required, no default). Inside compose `VAULT_ADDR=http://vault:8200`.
- Non-secret DB location stays in env: `DB_HOST`, `DB_PORT`, `DB_NAME` (defaults = today's local values: catalog `localhost`/`5432`/`catalog`, compliance `localhost`/`5433`/`compliance`). `DATABASE_URL` is removed from both services.
- No application secret (DB passwords, `BFF_CLIENT_SECRET`, Vault root token, AppRole ids) appears as a default anywhere: code, `.env.example`, compose (`${VAR:?}` for them; `${VAR:-x}` stays for non-secret names/ports).
- Exception, decided with the user: the Keycloak and Grafana admin logins are tool access, not application secrets. They keep the fixed `admin`/`admin` in `.env.example` and the compose defaults `${KEYCLOAK_ADMIN_PASSWORD:-admin}` / `${GRAFANA_ADMIN_PASSWORD:-admin}`.
- Error messages and logs never include `secret_id`, tokens or secret values.
- Realm test users (`admin`/`admin`, `customer`/`customer`) stay versioned as demo data.
- Commits: Conventional Commits in Portuguese, ending with `Refs #45` and the `Co-Authored-By` line.
- Each service follows its own `CLAUDE.md` (Clean Architecture: Vault code lives in `infra/config`, never in `core`).

## Review Focus

1. **Vault down or unreachable at service start** → the service exits with a clear error naming Vault and the address, never a stack of undefined config. Tests in Tasks 2 and 3; manual check in Task 5.
2. **Password with URL-special characters** (`p@ss/w:rd`) → the DB URL is percent-encoded and still connects. Tests in Tasks 2 and 3; `make env` generates hex so real runs never hit it, but a hand-edited `.env` will.
3. **Existing `.env` holding only `BFF_PORT=8081`** (documented in today's README) → `make env` appends the missing keys and keeps the existing lines untouched. Check in Task 1.
4. **Vault container restarted** (dev mode loses everything) → `make vault` re-runs the bootstrap and it succeeds on a Vault that already has the roles, and on an empty one. Check in Task 1.
5. **A service's AppRole reads another service's path** → HTTP 403. Check in Task 1.
